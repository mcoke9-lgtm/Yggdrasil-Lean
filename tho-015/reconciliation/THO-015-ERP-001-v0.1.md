**Artifact:** THO-015-ERP-001

**Scope:** Reconcile the four authorized THO-015 probes against recovered adopted decisions and identify bounded follow-up work. No production changes.

## 1. Executive result

The four authorized probe slots now have recorded outcomes, but the evidence is not uniformly conclusive:

1. **Probe 1 — REPRODUCED:** a process terminated immediately after successful atomic snapshot replacement; retrying the same create request created a second record/version with identical content and new IDs.
2. **Probe 2 — FAIL:** malformed snapshot inputs were rejected in 11/11 tested cases, but reconciliation returned `AMBIGUOUS` where the adopted decision requires `UNCERTAIN` when history is malformed. A wrong-typed `event_type` was rejected via raw `TypeError`.
3. **Probe 3 — NOT APPLICABLE:** there are no per-record directories in the inspected single-JSON-snapshot storage design. This does not establish general symlink safety.
4. **Probe 4 — OBSERVATIONS REQUIRE QUALIFICATION:** current import behavior accepts several non-empty unusual identifiers and rejects an empty identifier; exact duplicate record IDs are rejected. However, the harness did not actually create two separate records whose IDs differ only by case. Its report's claim that case-distinct *record IDs* were accepted is therefore unsupported. The event-ID case distinction was tested separately and accepted.

The evidence phase can be closed as a first pass, but Probe 4's narrow case-collision claim should be corrected by a follow-up evidence-only test before it is used to support an implementation decision.

## 2. Decision-to-evidence reconciliation

### 2.1 Uncertain-commit retry / idempotency

**Relevant design concern:** the current CLI create operation has no request identity/idempotency token in the tested invocation. A successful persistence operation followed by lost acknowledgment can be retried as a new logical create.

**Evidence:** Probe 1 reproduced one persisted record after the child process exited with code 73 immediately after the real `os.replace`; a retry exited 0 and left two records and two versions with identical content but distinct record/version IDs.

**Classification:** Reproduced behavior / design gap. The test is specific to this failure boundary and runtime; it is not a universal claim about all storage failures.

**Smallest next work (proposal only):**
- Define the operation identity boundary before changing code: what uniquely identifies a retried logical create, who supplies or generates that identity, and how long it remains reserved.
- Decide whether idempotency belongs in the CLI/API contract, persisted store schema, provenance event model, or a coordinated layer.
- Specify replay behavior: same key + same request returns the original result; same key + different request is rejected as a conflict; unknown outcome remains safely reconcilable.
- Add regression tests for crash-after-replace, retry, repeated retry, and same-key/different-payload conflict only after the contract is adopted.

No idempotency design has been selected or implemented.

### 2.2 Malformed-history precedence and validation

**Relevant adopted decisions recovered:**
- Validate the complete history before calculating record-specific outcomes.
- Any malformed event anywhere in history yields `UNCERTAIN`, including an unrelated event and even where valid duplicate evidence also exists.
- `UNCERTAIN` takes precedence over `AMBIGUOUS`.
- Malformed events are rejected during reconciliation; malformed history is rejected before subsequent writes.
- Reconciliation has a separate read-only open path distinct from write-capable access.

**Evidence:** Probe 2 rejected 11/11 malformed snapshots, including malformed data in an event for another record. It also passed `history_state="malformed"` alongside duplicate matching evidence to the reconciliation function; actual result was `AMBIGUOUS`, expected `UNCERTAIN`.

**Classification:** Confirmed precedence mismatch at the tested reconciliation API boundary. End-to-end integration remains unverified: this probe did not establish that every caller loads and validates the entire history before invoking reconciliation or before allowing writes.

**Additional quality observation:** list-valued `event_type` produced raw `TypeError` ("unhashable type: 'list'") rather than a normalized provenance validation exception. The malformed input was rejected; exception normalization is a separate robustness concern.

**Smallest next work (proposal only):**
- Correct outcome precedence so malformed-history uncertainty is resolved before duplicate/record-specific classification.
- Add a full-history integration test where a malformed unrelated event coexists with valid matching duplicates.
- Verify write paths reject malformed history before any mutation.
- Verify read-only reconciliation access cannot mutate state.
- Normalize malformed input failures into the documented validation exception boundary, if that boundary is confirmed by the specification.

Do not change the adopted decisions to fit current behavior.

### 2.3 Symlinked record directories

**Evidence:** Probe 3 found the inspected implementation persists one JSON snapshot file and has no per-record directory traversal.

**Classification:** Not applicable to the stated probe target.

**Boundary:** Snapshot-path symlinks, parent-directory symlinks, path replacement races, and platform-specific behavior remain untested. They are different probes and are not silently added to the authorized four-probe scope.

**Smallest next work:** none for this probe. Any new filesystem-path probe requires separate scope authorization.

### 2.4 Identifier compatibility and L2 grandfathering

**Relevant adopted decision:** L2 — grandfather existing identifiers.

**Evidence actually produced:**
- Core Memory snapshot importer accepted non-empty values including `CON`, `AUX`, `.`, `..`, and `../outside` in the single-record test snapshots.
- Empty identifier was rejected.
- Exact duplicate record ID was rejected.
- Provenance ledger accepted two event IDs differing only by case (`Legacy-ID`, `legacy-id`).

**Harness limitation requiring correction:** the case-distinct Core Memory test did not create two records with IDs `Legacy-ID` and `legacy-id` in the same snapshot. It paired one record ID with a case-distinct version ID. Therefore, the evidence report's statement that case-distinct record IDs were accepted is not established by this run. The case-distinct event-ID result is established.

**Classification:** Preliminary importer observations; not a complete L2 conformance test. No claim is made that the sample identifiers exist in historical user data, or that they are safe as filesystem paths.

**Smallest next work (proposal only):**
- Correct the case-collision harness to create two records with case-distinct IDs in one snapshot, plus their versions, and test round-trip preservation.
- Include a separate exact-duplicate control case.
- If actual historical identifiers are available in an authorized fixture, test those verbatim; otherwise label synthetic values as synthetic.
- Preserve grandfathering of existing identifiers; do not infer a restrictive new grammar from these importer observations.
- Treat creation-time identifier policy as a separate normative decision, not a side effect of the import test.

## 3. Cross-cutting verification gaps

These remain unverified and must not be reported as passed:
- The full YIM-001 reconciliation call path validates the entire event history before record-specific reconciliation.
- Malformed history is rejected before every write-capable operation.
- Read-only reconciliation access is technically non-mutating.
- Idempotent create/retry behavior (no implementation exists in this evidence set).
- Case-distinct Core Memory record IDs in a single snapshot.
- Actual historical identifier corpus compatibility.
- Symlink safety for snapshot and parent paths.
- Windows and other non-Ubuntu runtime behavior.

## 4. Evidence integrity notes

- Probe 1's original evidence report contains a stale sentence saying Probe 2 had not started. That statement was true when the report was first written, but is superseded by the later Probe 2 report and run. This package records the chronology; it does not rewrite the earlier append-only evidence.
- Probe 2's report correctly distinguishes loader rejection from reconciliation precedence and acknowledges that end-to-end integration was not tested.
- Probe 3's N/A classification is limited to per-record directories.
- Probe 4's report overstates the Core Memory case-distinct record-ID observation; this package corrects the claim and identifies the missing test.

## 5. Change-control and disposition

This package is a reconciliation artifact, not an authorization to modify source or normative specifications.

**Proposed disposition:**
- Close the initial evidence-gathering pass with Probe 1 reproduced, Probe 2 failing, Probe 3 N/A, and Probe 4 preliminary/partially qualified.
- Preserve the two confirmed implementation concerns for design review: uncertain-commit duplicate creation and malformed-history precedence.
- Run one narrowly corrected Probe 4 harness as evidence-only follow-up, if the user wants the identifier claim completed.
