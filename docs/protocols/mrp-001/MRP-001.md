# MRP-001 Working Baseline 2026-11 — Revision 4

**Status:** Adopted  
**Adoption date:** 2026-11-10  
**Adopted text:** The Final Adoption Candidate presented in the adoption conversation, including editorial clarifications A9 and A10.

Candidate-004 remains frozen and unchanged, and is not adopted as the implementation. Candidate-005 and implementation work are not authorized by this adoption.

---

## 1. Purpose and Scope

**Purpose**  
Define a minimal, testable foundation for versioned memory records supporting stable identity, non-destructive revision, and explicit conflict annotation.

**Scope**  
In scope: the records module (minimal profile) and the rules needed for future modules to interoperate with it.  
Out of scope for the minimal profile: durable persistence, provenance, events, integrity sealing, recovery procedures, networking, multi-tenancy, and policy engines.

### 1.1 Inherited Normative Core

The sole inherited requirements remain the six capabilities from the original invitation:

1. Stable memory record identifiers.
2. Creation of initial memory versions.
3. Revision without destruction of earlier versions.
4. Retrieval of individual versions.
5. Preservation of version relationships.
6. Explicit handling of conflicting revisions.

---

## 2. Profiles

| Profile | Status | Contents |
|---------|--------|----------|
| **Minimal records-module profile** | Normative | Inherited capabilities + strict JSON + directional conflicts |
| **Reference-implementation profile** | Non-normative | Python standard-library only, no cloud/paid services, plus the quality attributes demonstrated by Candidate-004 |
| **Durable profile** | Optional higher profile | Minimal profile + durable persistence that preserves identifiers, parents, content, metadata, and conflicts across restarts |
| Future profiles (provenance, events, integrity, recovery) | Not yet defined | — |

An implementation that satisfies the minimal records-module profile conforms to this baseline even if it is purely in-memory.

---

## 3. Mandatory Core Requirements (Minimal Profile)

- The six inherited capabilities (§1.1).
- Content (and metadata when present) MUST be serializable under the JSON data model. An implementation MUST reject values that are not representable in JSON, including but not limited to `NaN`, `+Infinity`, `-Infinity`, functions, and non-finite floating-point values. Validation MUST be applied recursively to nested arrays and objects. Rejection MUST occur before a version is created or revised.
- Conflict annotations are directional. Reciprocal annotations are not required. An implementation conforms to directional conflict semantics if it can store and later retrieve a one-way conflict annotation without requiring or automatically creating the reverse annotation.

---

## 4. Verified Candidate-004 Properties

**(Quality attributes, not mandatory protocol requirements)**

- Append-only version graph
- Immutable version snapshots
- Collision-checked identifier allocation
- Deep-copy isolation of content and metadata
- Metadata type validation before content validation
- Cycle rejection
- Duplicate-parent normalization
- Explicit distinction between divergence (multiple tips) and conflict annotations

These remain valuable evidence of implementation quality. They are not required for conformance to the minimal profile unless later elevated.

---

## 5–8. Proposed Extension Areas

**(Not required for minimal-profile conformance)**

**Provenance, Events, Integrity** — Proposed extension points only. No structured fields are mandated.

**Persistence** — Durable persistence is an **optional higher profile**. An in-memory implementation may fully conform to the minimal records-module profile.

**Recovery**

| Concern | Status |
|---------|--------|
| Non-destructive preservation of earlier versions | Satisfied by the version graph |
| Competing revisions and unresolved conflicts remain visible | Supported by multiple tips + directional conflict annotations |
| Formal restore operation | Unspecified |
| Damaged- or incomplete-history representation | Unresolved |
| Orphaned external-reference policy | Deferred to future recovery/import work |

---

## 9. Conflict Semantics (Normative)

Conflict annotations are directional.  
A system MUST NOT require the reverse annotation to be present.  
An implementation conforms to directional conflict semantics if it can store and later retrieve a one-way conflict annotation without requiring or automatically creating the reverse annotation.  
Conflict resolution rules, lifecycle, and a precise definition of “unresolved conflict” remain unresolved.

---

## 10. Module Boundaries

Future modules interact with records by reading versions, creating new versions, and storing auxiliary data in metadata or external stores keyed by record/version identifiers.  
Orphaned-reference policy is deferred.

---

## 11. Security

The records module performs no authentication or authorization. Access control and encryption are the responsibility of callers or future profiles.

---

## 12. Compatibility and Breaking-Change Policy

**(Authorized)**

- Addition of optional fields or operations is non-breaking **only when** backward compatibility is preserved, including appropriate handling of unknown optional fields.
- Removal or semantic alteration of any inherited or previously adopted requirement is breaking and requires a new baseline version.
- Changes confined to Proposed extension areas or optional profiles do not affect minimal-profile conformance.
